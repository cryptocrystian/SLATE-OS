## 3. Source changes shipped this sprint

### 3.1 Print isolation CSS — `styles/globals.css`

Adds an aggressive `@media print` block that hides every body-level sibling that is NOT marked `[data-deliverable-export]`. This **kills the Chrome extension overlay leak** ("Claude is active in this tab group") + any future app-chrome/extension/overlay DOM from bleeding into browser Save-as-PDF output. Inside the export wrapper, shadows are forced off and full-bleed width restored.

```css
@media print {
  body > *:not([data-deliverable-export]):not(script):not(style):not(link) {
    display: none !important;
  }
  [data-deliverable-export] {
    display: block !important;
    width: 100% !important;
    max-width: none !important;
    margin: 0 !important;
    padding: 0 !important;
    background: #ffffff !important;
  }
  [data-deliverable-export],
  [data-deliverable-export] * { box-shadow: none !important; }
  body > div:not([data-deliverable-export]):not(#__next) { display: none !important; }
}
```

**Acceptance verification (post-deploy):** operator opens any of the 5 deliverable routes on staging with the Claude.ai browser extension active, drives `Ctrl-P → Save as PDF`, and `pdftotext` the result. The phrase `Claude is active in this tab group` (or any equivalent extension overlay text) MUST NOT appear.

### 3.2 `data-deliverable-export` attribute on every deliverable container

Five document component roots now declare the canonical export attribute so the print isolation CSS knows to preserve them:

| Component | Attribute value |
|---|---|
| `components/reports/report-pdf-candidate-document.tsx` | `data-deliverable-export="report-candidate"` |
| `components/proposals/proposal-candidate-document.tsx` | `data-deliverable-export="proposal-candidate"` |
| `components/proposals/sow-draft-document.tsx` | `data-deliverable-export="sow-draft"` |
| `components/reports/client-report-share-document.tsx` | `data-deliverable-export="client-report-share"` |
| `components/proposals/client-proposal-share-document.tsx` | `data-deliverable-export="client-proposal-share"` |

The attribute is **purely structural** — no rendering / data / boundary change. It exclusively enables the `@media print` CSS rule above.

### 3.3 Session-status auto-update on first ready response — `lib/intake/offline-actions.ts::markStakeholderResponseReadyForSynthesisAction`

After the response status flips to `ready_for_synthesis`, the action now also auto-advances `stakeholder_intake_sessions.status` from `not_started` to `completed`, scoped to the parent session, race-safe via the `WHERE status='not_started'` filter (idempotent — no-op if already `in_progress` / `completed`). Failure is best-effort logged but does NOT block the response promote.

**Effect on AI report-section synthesis prompts:** when the prompt context reads `session.status`, it will see `completed` for sessions that have ≥ 1 ready response. The synthesis no longer claims "intake has not started" while the response chain is rich. No prompt change required — the data model now tells the truth.

**Historical backfill — Meridian only:** the Meridian fixture's 4 sessions still carry `status='not_started'` from before this fix landed. The auto-update only fires on **future** `mark ready` transitions. To backfill Meridian without operating outside the canonical action layer, the simplest path is for the operator to drive one `Mark ready` re-action through the deployed UI on any one response per session — the action is idempotent (returns `{ok:true}` for already-ready responses) and re-firing it on a ready response will trigger the new session-status update branch. **No direct SQL UPDATE is required, and no SQL UPDATE is authorized by this sprint.** Documented in `docs/60` § 5 follow-on instructions.

## 6. Client-facing vs operator-mode distinction

**Foundation shipped this sprint:** every deliverable container carries `data-deliverable-export` so the next sprint can layer the `viewerMode` prop + UI toggle on top without touching the print isolation.

**Not shipped this sprint (sized in § 7 backlog item B):** the `viewerMode: "operator" | "client-facing"` prop on the report PDF candidate + proposal candidate documents, the on-screen-only toggle button (`print:hidden` so it doesn't bleed into exports), and the conditional-render logic that strips `IdentityHeader` UUIDs / `ClaimGuardStrip` scan metadata / `"Generated by"` label / footer `Snapshot {id}` in client-facing mode.

**Public `/r` and `/p` routes are unaffected** by the missing toggle — they use `ClientReportShareDocument` + `ClientProposalShareDocument`, which already filter every operator metadata surface by component design (per `client-report-share-document.tsx:23-32` + `client-proposal-share-document.tsx:25-45`). The public routes are the canonical client-safe surface; the PDF candidate is operator-only. A client-facing PDF export from the PDF candidate page is the convenience layer the viewerMode toggle delivers — useful but not the only path. **The operator can already cleanly export a client-safe PDF today** by navigating to `/r/<token>` (logged-out, anonymous browser) and printing from there.
